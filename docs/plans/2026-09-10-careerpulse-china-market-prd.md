## 1. 背景与问题

### 1.1 现状

CareerPulse 目前是一个面向**美国就业市场**的自托管求职自动化平台：

- 14 个美国招聘源（LinkedIn、Dice、Indeed、Remotive、USAJobs、Greenhouse…）
- 数据库薪资字段单位为**美元/年**，过滤器默认 `$150k 年薪 / $95 时薪`
- 内置 **2025 美国联邦 + 50 州税率**、W2/1099/C2C 报税、州税估算、生活成本归一化
- 表单与问卷按美国惯例设计：**EEO 平权问卷、work authorization、签证赞助、安全许可（clearance）、兵役记录**
- 公司情报依赖 **Glassdoor 评分**
- 沟通渠道默认**邮件**（申请邮件、跟进邮件、邮件摘要）

界面层已完成中英双语（默认 `zh-CN`），但**业务层完全美国化**：中文界面下展示的是"$150,000 起、需要工作授权、Glassdoor 3.9 分"。这是"翻译过的美国产品"，不是"中国产品"。

### 1.2 中国求职者的真实痛点

| 痛点 | 现状描述 |
| --- | --- |
| 平台割裂 | BOSS 直聘、智联、51job、猎聘各有一套账号、简历、沟通记录，无法统一看"我到底投了哪些" |
| 主动沟通成本高 | BOSS 直聘是**沟通制**而非投递制，"打招呼"话术决定 HR 是否回复；一天聊 30 个 HR，聊过谁、谁没回，全靠脑子记 |
| 简历规格不同 | 国内简历需要照片位、政治面貌、生源地、应届/往届、单页、DOCX 优先；现有系统生成的是美式 resume |
| 薪资口径不同 | 国内讲月薪 + 13/14/15 薪，"总包"含年终奖 + 股票 + 签字费；现有系统只会显示年薪美元 |
| 到手工资不透明 | 五险一金 + 个税累计预扣 + 年终奖单独计税，offer 之间"总包 45 万"和"月薪 3.5 万 ×14"哪个到手多，算不清 |
| 面试准备材料散落 | 八股文、算法题、项目深挖、HR 面问题散落在牛客 / 掘金 / 收藏夹，没有按岗位组织的准备清单 |
| 记录无处沉淀 | 无本地化工具，数据留在各平台（或 Excel），无法复盘"哪个渠道转化率最高" |

### 1.3 产品定位

> **一句话**：一个跑在你自己电脑上、说中文、认 BOSS 直聘的求职作战台 —— 你在平台上正常浏览，它负责记下来、帮你判断值不值得聊、提醒你谁还没回、并且把简历和面试准备做到能直接投出去。

**不做**：不做 SaaS、不代投、不绕过平台风控、不集中爬取平台数据、不共享用户数据。

## 2. 目标用户与场景

### 2.1 主用户画像（一期唯一画像）

- **身份**：中国内地求职者，以**互联网 / 软件研发类岗位**为主（后端、前端、算法、测试、运维、数据）
- **经验**：1–10 年，社招为主；应届生为次要场景
- **技术能力**：能安装浏览器扩展、能填 AI API Key、能跑 Docker
- **设备**：Mac / Windows 笔记本 + Chrome / Edge
- **求职方式**：以 BOSS 直聘为主战场，日均主动沟通 5–30 人
- **部署方式**：本机 / 家用 NAS 跑服务，浏览器扩展连本机

### 2.2 核心使用场景

**场景 A：日常刷岗（最高频，每天 1–2 次，每次 10–20 分钟）**
> 小李晚上打开 BOSS 直聘搜"Golang 后端"，扩展在每个职位卡片右上角显示匹配分角标（86 / 62 / 41），他一眼扫过只点开 80 分以上的，点"收藏"直接进 CareerPulse 队列 → 打开看板，本周 23 条新职位里 7 条 85 分以上，逐条看匹配理由和技能缺口。

**场景 B：批量打招呼（每天 1 次，10–30 次）**
> 小李在队列里勾选 12 个高匹配职位 → 系统按职位生成 12 条不同的招呼语（引用具体项目经历，不是群发模板）→ 他逐条复制粘贴到 BOSS 聊天框 → 系统自动把状态标记为"已联系"并起 3 天跟进计时。

**场景 C：跟进与复盘（每周 1 次）**
> 看板"待跟进"列有 9 个人 3 天没回 → 系统给出二次跟进话术 → 他重发一轮，标记结果 → 有人回复后转为"已投递"→ 面试邀约后进入面试流程，日历自动生成提醒。

**场景 D：面试准备（拿到面试后，集中 1–2 小时）**
> 小李把某大厂后端岗加入题库 → 系统按该 JD 的技术栈（Go / MySQL / Redis / K8s）生成问题清单（八股文 + 项目深挖 + 场景设计）→ 他逐题写要点草稿 → 模拟面试模式对着问题自述，记录卡壳点。

**场景 E：offer 比较（收尾阶段）**
> 拿到 3 个 offer → 输入「月薪 3.5 万 ×14 + 股票 20 万/4 年」vs「月薪 4 万 ×13 + 签字费 5 万」→ 系统按城市社保基数与公积金比例算到手月薪、年总包、年终奖单独计税后的净额 → 输出对比表。

### 2.3 关键用户旅程（首次使用，目标 < 15 分钟）

```
安装服务(2min) → 安装扩展(1min) → 上传中文简历，AI 解析出画像(3min)
  → 填 AI API Key，一键测试连通(2min) → 打开 BOSS 直聘搜索页(1min)
  → 页面上出现匹配分角标(即时) → 收藏 5 个职位 → 看板里逐条看匹配理由(5min)
  → 生成第一条招呼语并复制
```

**里程碑判据**：从安装到复制出第一条招呼语 ≤ 15 分钟。

## 3. 成功指标

自用产品的指标目标是"证明闭环成立"，不是增长。

| 指标 | 定义 | 一期目标 |
| --- | --- | --- |
| 首次价值时间 | 安装 → 复制出第一条招呼语 | ≤ 15 分钟 |
| 采集准确率 | 收藏的职位中字段（标题/公司/城市/薪资/经验/学历）完整率 | ≥ 95% |
| 采集成功率 | 一键收藏的请求中成功入库比例 | ≥ 98% |
| 匹配分可用性 | 用户对 80 分以上职位的"值得聊"认同率（抽样自评） | ≥ 70% |
| 沟通转化 | 已联系 → 有 HR 回复的比例 | 相对平台基线提升 ≥ 30% |
| 跟进覆盖率 | 超过 3 天未回复且被跟进的比例 | ≥ 80% |
| 周复盘使用 | 连续 4 周每周至少 3 天使用 | 达成 |
| AI 单次成本 | 单职位匹配打分成本（DeepSeek） | ≤ ¥0.01 |

## 5. 平台接入方案（技术前提）

这是本 PRD 最关键的可行性论证：**BOSS 直聘没有公开 API，且风控体系（`__zp_stoken__` 签名、滑块验证、账号行为风控）明确针对自动化。** 因此方案必须建立在"用户自己的浏览器、自己的登录态、正常的浏览行为"之上。

### 5.1 三层架构

```
┌─────────────────────────────────────────────────────────────┐
│ ① BOSS 直聘页面（用户已登录，正常浏览/搜索）                    │
│    用户行为：输关键词、翻页、点开职位详情                        │
└───────────────┬─────────────────────────────────────────────┘
                │ 扩展注入（ISOLATED world）
┌───────────────▼─────────────────────────────────────────────┐
│ ② Chrome 扩展（MV3）                                          │
│    · boss-capture.js：页面上下文内 fetch（携带页面自身 cookie/  │
│      stoken 签名），读 listings / job detail 接口响应           │
│    · overlay.js：注入匹配分角标、收藏按钮、侧边浮层              │
│    · background.js：握手 + 批量带节流上传                       │
└───────────────┬─────────────────────────────────────────────┘
                │ http://127.0.0.1:<port>/api/capture  (Bearer token)
┌───────────────▼─────────────────────────────────────────────┐
│ ③ CareerPulse 服务（FastAPI + SQLite，仅监听 loopback）        │
│    归一化 → 去重 → 入库 → AI 匹配打分 → 看板呈现                 │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 采集实现方式（优先级从高到低）

| 方式 | 说明 | 采用 |
| --- | --- | --- |
| **C1 页面上下文 fetch** | 注入脚本在页面 world 内调用 BOSS 自身的接口，自动携带页面的 cookie 与签名参数。**首选** | ✅ 主路径 |
| **C2 DOM 解析** | 从已渲染的列表卡片 / 详情节点读取文本。C1 接口变更时兜底 | ✅ 兜底 |
| **C3 用户复制粘贴** | 详情页"复制 JD"→ 粘贴到浮层。任何情况下都可用的最终兜底 | ✅ 兜底 |

**必须遵守的采集纪律（写进代码，不只是文档）：**

1. **只采集用户已经看到的页面**：只处理当前页面已渲染的内容，扩展**不主动翻页、不批量遍历搜索结果**。
2. **节流**：相邻两次采集请求间隔 ≥ 3 秒；单次会话采集上限 100 条（可配），超限提示用户。
3. **不伪造、不重放**：不构造签名、不缓存 token、不重放历史请求。
4. **只读**：绝不调用任何写操作接口（发消息、投递、改简历）。
5. **可关闭**：扩展浮层提供「暂停采集」开关，状态存 `chrome.storage.local`。

### 5.3 扩展 ↔ 服务握手与鉴权

现有扩展硬编码 `http://localhost:8085/*`。中国版服务端口可变，且所有写接口必须鉴权。

| 项 | 设计 |
| --- | --- |
| 端口发现 | 服务启动时把实际端口写入用户数据目录 `data/extension-bridge.json`；扩展首次连接依次探测 8085 / 8086 / 8087 / 8088 |
| 令牌 | 服务首次启动生成 32 字节随机 token，存 `data/extension-token`；用户在设置页点击「连接扩展」复制；扩展存 `chrome.storage.local.bridge_token` |
| 请求头 | `Authorization: Bearer <token>`；服务拒绝无 token 的 `/api/capture/*` 请求（返回 401） |
| 来源校验 | 服务校验扩展固定扩展 ID（`Origin: chrome-extension://<id>`），非白名单来源一律拒绝 |
| CORS | 仅允许 `chrome-extension://<id>` 与 `http://127.0.0.1:<port>` |
| 监听地址 | **只监听 `127.0.0.1`**，禁止 `0.0.0.0`（避免局域网内他人调用本地库） |

> ⚠️ 安全要点：`127.0.0.1` 服务若被任意网页调用，等同本地数据泄露。**token + Origin 白名单不可省略。**

### 5.4 扩展权限收敛

现有 `manifest.json` 的 `content_scripts.matches` 为 `<all_urls>`。中国版必须收窄：

```json
"host_permissions": [
  "https://*.zhipin.com/*",
  "http://127.0.0.1/*"
],
"content_scripts": [{
  "matches": [
    "https://www.zhipin.com/web/geek/job*",
    "https://www.zhipin.com/job_detail/*"
  ],
  "js": [ ... ],
  "run_at": "document_idle"
}]
```

二期新增平台时只追加域名，不得退回 `<all_urls>`。

### 5.5 采集字段与归一化

`app/extension_bridge/normalizers/boss.py` 负责把 BOSS 原始结构映射为统一 `JobListing`：

| 统一字段 | BOSS 来源 | 归一化规则 |
| --- | --- | --- |
| title | 职位名 | 去空白、去 `【】` 前缀 |
| company | 公司名 | 去「招聘」后缀、全角转半角 |
| city / district | 城市 / 区域 | 匹配城市字典；缺失时城市留空并标 `city_unknown` |
| salary_min / salary_max | 薪资文本如 `25-40K·13薪` | 解析为**月薪元**：25000 / 40000；`·13薪` → `months_per_year=13` |
| salary_negotiable | `面议` | 置 1，min/max 置 NULL |
| experience_req | `3-5年` / `经验不限` | 枚举：`不限/应届/1年以内/1-3年/3-5年/5-10年/10年以上` |
| education_req | `本科` / `学历不限` | 枚举：`不限/大专/本科/硕士/博士` |
| company_size | `100-499人` | 枚举：`0-20/20-99/100-499/500-999/1000-9999/10000+` |
| company_stage | `B轮` / `已上市` | 枚举：`未融资/天使轮/A轮/B轮/C轮/D轮及以上/已上市/不需要融资` |
| job_labels | `五险一金`、`双休`、`零食下午茶` | 文本数组，JSON 存储 |
| description | 职位描述 | 保留原始文本（原文不翻译） |
| source_platform | — | 固定 `boss`，预留 `zhaopin` / `job51` / `liepin` |
| capture_method | — | `api` / `dom` / `manual` |
| external_id | 职位加密 ID | 平台侧唯一 ID，用于跨来源去重 |

**去重键**：`sha1(f"{source_platform}:{external_id}")` 优先；无 `external_id` 时回落 `sha1(platform + normalized_title + normalized_company + city)`。

#### 6.4.2 回传流程

```
用户点击收藏
  → content script 发消息给 background
  → background 从 chrome.storage.local 取 bridge_token
  → POST 127.0.0.1:<port>/api/capture/job  { platform, payload, capture_method }
  → 服务归一化 → 去重 → 入库 → 立即返回 { job_id, is_new, title, company }
  → 扩展把 job_id 缓存进 localStorage，按钮直接变「★ 已收藏」
  → 服务的后台任务异步做 AI 精细打分 → 分数通过 GET /api/capture/score/<job_id> 轮询（或扩展静默刷新）
```

**幂等**：同一 `external_id` 重复回传返回 `is_new: false` + 既有 `job_id`，扩展不报错。

**离线容错**：服务未启动时，采集数据暂存 `chrome.storage.local` 队列（上限 200 条），下次握手成功后自动补传，浮层提示「本地服务未连接，已暂存 N 条」。

| --- | --- | --- |
| 养老保险 | 8% | |
| 医疗保险 | 2% (+ 大病固定额，按城市) | |
| 失业保险 | 0.5%（部分城市 0%） | |
| 住房公积金 | 5%–12%（用户选） | |
| 工伤 / 生育 | 个人 0 | 单位承担 |

- 缴费基数 = `clamp(月薪, 城市社保下限, 城市社保上限)`；公积金基数单独 `clamp(月薪, 城市公积金下限, 上限)`
- 各地比例/上下限存 `app/data/social_insurance/{城市}.json`，含 `effective_year`、`source_note`、`updated_at`

**个人所得税（居民个人工资薪金，累计预扣法）**

```
累计预扣预缴应纳税所得额 = 累计收入 − 累计免税收入 − 累计减除费用(5000×月数)
                          − 累计专项扣除(五险一金个人部分) − 累计专项附加扣除 − 累计其他扣除
本期应预扣预缴税额 = (累计应纳税所得额 × 预扣率 − 速算扣除数) − 累计已预扣预缴税额
```

预扣率表（七级超额累进）：`≤36000→3%/0`、`≤144000→10%/2520`、`≤300000→20%/16920`、`≤420000→25%/31920`、`≤660000→30%/52920`、`≤960000→35%/85920`、`>960000→45%/181920`

**年终奖**：两种方式对比展示
- 单独计税：`年终奖 ÷ 12` 定税率 → `年终奖 × 税率 − 速算扣除数`
- 并入综合所得：并入当年累计计税
- 输出「哪种更省税 + 差额」

**输出**：到手月薪（逐月，体现累计预扣导致的"前低后高"）、年度到手总额、年总包、单位用人成本（可选）、个税与五险一金明细构成。

#### 6.10.2 数据可信度要求（硬性）

1. 每个城市数据文件必须带 `effective_year` 与 `source_note`（如"参照 2026 年度上海市社保缴费基数上下限"）。
2. 界面显著标注：**「测算结果仅供参考，实际以当地社保/税务口径为准」**，并显示数据年份。
3. 数据超过 **18 个月**未更新时，界面顶部黄色提示条「社保数据可能过期，点击核对」。
4. 结果页提供「导出明细（CSV）」与「一键对比 2–3 个 offer」。
5. offer 对比表列：月薪、薪数、年总包、到手月薪（首月/稳定月）、年度到手、公积金年入账、股票/签字费折年、备注。

## 7. 数据模型与迁移

### 7.1 迁移策略

| 项 | 方案 |
| --- | --- |
| 机制 | 复用现有 `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 的幂等迁移风格，新增 `schema_migrations` 表记录版本号 |
| 37 张现有表 | **不重建**，只增列；删除表（`eeo_responses`、`military_service`）走 `DROP TABLE IF EXISTS` |
| 美元→人民币 | 自用工具，**不做汇率换算**；现有 `jobs` 行若存在，按设置项选择「全部清空（推荐）」或「标记为历史数据」 |
| 城市字典 | `app/data/cities.json` 随包发布，启动时校验版本号，落后则提示更新 |
| 社保数据 | `app/data/social_insurance/*.json` 逐城市文件，独立于代码更新 |
| 备份 | 迁移前自动复制 DB 到 `data/backups/jobfinder-YYYYMMDD-HHmm.db`，失败可回滚 |

### 7.2 多用户预留（D4）

一期不做账号体系，但为二期铺路，**只做三件事**：

1. 所有用户相关表加 `user_id INTEGER NOT NULL DEFAULT 1`（`jobs` / `applications` / `resumes` / `contacts` / `user_profile` / `reminders` / `saved_views` / `interview_*`）
2. 所有单例配置表（`search_config`、`ai_settings`、`email_settings`、`embedding_settings`，现为 `id INTEGER PRIMARY KEY CHECK (id = 1)`）改为 `(user_id, id)` 主键或增加 `user_id` 唯一索引
3. 数据访问层集中到 `app/repositories/*.py`，所有查询从 `current_user()` 取 `user_id`（一期恒返回 1）

## 9. 非功能需求

### 9.1 隐私与合规

| 项 | 要求 |
| --- | --- |
| 数据本地 | 简历、职位、沟通记录**只存本地 SQLite**，不上传任何第三方；服务只监听 `127.0.0.1` |
| AI 外发透明 | 调用云端 AI 前，明确展示「将发送：简历摘要 + 职位描述（约 N 字）到 <provider>」；提供「仅使用本地模型」开关 |

| 扩展权限 | 只申请目标平台域名（见 5.4），不申请 `<all_urls>`、不申请 `cookies`、不申请 `tabs` |
| 平台账号安全 | 不读取、不存储、不导出 BOSS 直聘的 cookie/token；不模拟登录 |
| 平台条款 | README 与首次启动页明确声明：本工具仅协助**用户本人**整理自己浏览到的信息，不批量爬取、不绕过风控、不代替用户操作；使用风险由用户承担 |
| 个人信息保护 | 自用工具不涉及"个人信息处理者"义务；若二期转为多用户产品，需补充《个人信息保护法》合规设计（告知同意、目的限定、删除权） |
| 免责 | 薪资测算页、AI 匹配页、AI 生成内容均标注「仅供参考，请以官方口径为准」 |

### 9.2 性能

| 指标 | 目标 |
| --- | --- |
| Web 首屏 | < 800ms（本地，冷启动后） |
| 扩展收藏 → 服务入库 | < 500ms（不含 AI） |
| 本地粗排分（列表页） | < 5ms / 条 |
| AI 精细打分（DeepSeek） | < 8s / 条，失败重试 2 次并降级为粗排分 |
